# Работа со сборкой

- Исходная точка: официальный экспорт Caves and Dungeons 1.4, project 971867/file 6164816, SHA256 `b7d41eea56ebf42c7eb115b00cfc2840cda28f1d222ca9edc853b3aeec09df5e`. Minecraft 1.20.1, Forge 47.3.7, Java 17.
- `tools/upstream-lock.json` хранит историю автора. Восстанавливать текущую поставку только по `tools/distribution-lock.json` через `tools/restore_distribution.py`; старый импорт не должен возвращать заменённые JAR.
- Итоговый состав, helper и активные locks меняет один владелец последовательно. Для каждой замены сохранять старую/новую версию, SHA256, причину и последствия для миров. Общие зависимости без необходимости не обновлять.
- Имя пресета строго **Шахты с Модами**, ID `caves_and_dungeons:modded_mines`. Это собственный пресет с исходной генерацией сборки, не восстановленная реализация видео. Ограничение действует на создание и пересоздание, не на загрузку существующих миров. При отсутствии обязательного пресета создание отменять без подстановки другого.
- У helper Java 17, `pack_format=15`, клиентские mixin только на клиенте. После изменений проверять реальные точки SRG, native serializer, оба списка выбора, datapack reload и реальный вход в мир. Offline proof не заменяет полный клиент.
- При новом/обновлённом моде проверять новые записи мира, инвентаря, permission/caster/owner и отложенные действия; фиксировать, требуется ли Safety. Унаследованная ошибка не становится PASS лишь потому, что процесс продолжил запуск.
- Для каждого фактического mod ID, включая вложенные Forge-библиотеки, хранить проверенную официальную HTTPS-страницу. Не подменять страницу чужим одноимённым проектом. Недоступный подтверждённый адрес хранить с `available:false`; исключения встроенных компонентов документировать.
- Временные сборки, игровые стенды и сырые логи находятся в игнорируемом `artifacts`; воспроизводимые исходники остаются в `tools`. Личные пути и необработанные логи не публиковать.
- Перед коммитом выполнить проверки README и обязательный Release-профиль лаунчера. Сначала публикуются payload, затем манифест и только затем карточка каталога. Существующие записи live-каталога сохранять.

- Русские достижения поддерживать через helper resources и единственный display-only override в обязательном встроенном датапаке; не перепаковывать авторские JAR и не менять criteria/requirements/rewards ради перевода. При изменении модов повторять `tools/russian-advancements/audit.py` и native ru_ru/en_us проверку приоритета, включая существующий мир.
- Квестбук генерирует `tools/quests/generate.py` из реальных достижений; поддерживать отсутствие всех наград и расходования предметов. Основной маршрут не должен требовать закрытого Незера; условно выключенные достижения не добавлять как активные задания. После правок прогонять отдельные `tools/quests` тесты и `--verify-only`; `config/ftbquests/quests/**` остаётся pack-owned.

## Сохранение диагностики при обновлениях автора

- После переноса новых авторских файлов сохранять pack-owned слой: `config/log4j2.xml`, `launcher/jvm-args.txt`, `launcher/pack-owned.txt`, `tools/network_logging_policy.py`, `tools/network-logging-policy.json`. Не заменять весь репозиторий одним авторским экспортом.
- В независимой исходной копии после импорта выполнить `python -B tools/network_logging_policy.py prepare --pack .`, затем `verify --pack .`; актуализировать затронутые support-lock записи по точным байтам. Это реальный ручной процесс подготовки, не автоматический апдейтер автора.
- Публикация и verify-only обязаны вызывать read-only `network_logging_policy.verify(pack)` до сбора/проверки assets. Не вызывать prepare из генератора, CI-публикации или работающего лаунчера; не отключать этот guard ради новой версии.
- Ownership только `config/log4j2.xml`, без нового `config/**`. Другие личные конфиги сохранять; отличающуюся старую копию этого файла обновление лаунчера сохраняет в PackConflicts.
- На новой версии Minecraft/загрузчика повторно проверить настоящий caller, logger и четыре Throwable-сообщения; конфиг не исправляет причину разрыва связи и не доказывает игровой запуск.
